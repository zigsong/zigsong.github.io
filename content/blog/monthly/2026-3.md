### css `zoom` vs `scale()`

- **zoom**
	- 요소 크기가 실제로 바뀜 → 주변 레이아웃에 영향 줌
	- 브라우저 기본 줌처럼 동작 (공간 차지)
	- 원점이 항상 왼쪽 상단

- **scale** (transform)
	- 시각적으로만 커지고 실제 공간은 그대로
	- 주변 레이아웃에 영향 없음 (겹침 발생 가능)
	- `transform-origin`으로 원점 조절 가능
	- GPU 가속 → 애니메이션에 훨씬 유리

### git rev-parse
    
Git 내부 객체나 레퍼런스를 실제 값으로 변환해주는 저수준 명령어

**현재 커밋 해시 얻기**

```bash
git rev-parse HEAD          # 전체 해시
git rev-parse --short HEAD  # 짧은 해시 (예: a3f2c1b)
```

**현재 브랜치 이름**

```bash
git rev-parse --abbrev-ref HEAD  # main, feature/login 등
```

**git 루트 디렉토리 경로**

```bash
git rev-parse --show-toplevel  # /Users/me/myproject
```

**지금 git 저장소 안에 있는지 확인**

```bash
git rev-parse --is-inside-work-tree  # true/false
```

사실 직접 터미널에 치는 경우는 드물고, 거의 항상 스크립트 안에서 쓴다.

```bash
# 배포 스크립트에서 현재 커밋 태깅
VERSION=$(git rev-parse --short HEAD)
docker build -t myapp:$VERSION .

# 프로젝트 루트 기준으로 파일 경로 잡기
ROOT=$(git rev-parse --show-toplevel)
cp $ROOT/config/.env.example $ROOT/.env

# git 저장소인지 체크 후 작업
if git rev-parse --is-inside-work-tree > /dev/null 2>&1; then
	echo "git 저장소입니다"
fi
```

Claude Code는 auto memory 디렉토리를 `~/.claude/projects/<repo-hash>/`로 관리하는데, 그 repo-hash 만들 때도 내부적으로 `git rev-parse`를 쓰는 식이다.
    
### CBT vs OBT vs GA

**🧪 CBT (Closed Beta Test)**

- **의미:** 비공개 베타 테스트.
- **대상:** 선발된 소수의 인원이나 사전 신청자.
- **목적:** 핵심 재미 요소 검증, 치명적인 버그 수정. "우리 서비스가 돌아는 가나?"를 확인하는 단계

**🔓 OBT (Open Beta Test)**

- **의미:** 공개 베타 테스트.
- **대상:** 누구나 참여 가능.
- **특징:** 정식 출시 직전 단계로, **서버 부하 테스트**가 주 목적

**🚀 GA (General Availability)**

- **의미:** 정식 출시 (범용 가용성).
- **대상:** 전 세계 모든 사용자.
- **특징:** "이제 우리 제품은 완성되었고, 공식적인 기술 지원을 보장한다"는 선언
- **마케팅 관점:** 이때부터 **본격적인 대규모 광고(UA 마케팅)**를 집행한다. 우리가 앞서 이야기한 **애드몹(AdMob)**이나 **DSP**를 통해 유저를 대량으로 끌어모으는 시점이 바로 이 GA 단계이다.
- `micromatch`
	- JavaScript 및 Node.js 환경에서 파일 경로 등을 매칭할 때 사용되는 고속 와일드카드(glob) 매칭 라이브러리
	- https://github.com/micromatch/micromatch

### AI로 빨리 만드는 팀보다 '덜 흔들리는' 팀이 이기는 이유

AI를 활용한 바이브 코딩으로 개발 속도는 기하급수적으로 빨라졌지만, 이전과는 다른 미묘한 오류와 불확실성들에 주의해야 한다.

결국 최종 검토와 승인을 내리는 것은 사람이고, 정답을 맞추는 능력이 아닌 실패를 통제하는 것이 중요한 시대가 온다.

### AI가 코드를 쓰는 시대, 개발자의 진짜 역량이 드러난다

지난 주 내가 올린 푸념과는 다른 논조의 글이다. 

이제 개발자는 작성자가 아닌 의사결정권자로 이동했다는 것, 코드에 대한 책임은 여전하다는 점에는 아직까지 대부분 동의한다. 

AI로 '동작'하는 코드를 만들어낼 수는 있겠지만, 결국 소프트웨어의 품질은 쉽게 얘기할 수 없는 문제다. 

AI가 그저 수많은 프로젝트에서 긁어온 '그럴듯한 패턴'으로 짜낸 코드의 집합들에서, 어디까지 경계를 짓고 추상화를 입힐 것인지 결정하는 것은 숙련된 개발자의 몫이다. 

동료 개발자들과 코드를 살펴보다 보면 "뭔가 이상한데"로 시작되는 암묵지가 여전히 존재하는 이유가 아닐까? 

업무의 여러 지점들에서 AI에게 넘겨도 될 것과 넘기지 말아야 할 지점을 구분하고, 의도적으로 직접 설계를 해보며 구현의 고통을 느껴보는 시간이 모든 개발자에게 필요한 시점이다. 

AI로 개발하는 풍경은 분명 많이 달라졌지만, 어쩌면 많은 사람들의 말대로 본질은 변하지 않았을 지도 모르겠다. 

**Ref** https://evan-moon.github.io/2026/02/10/developer-in-ai-era/
